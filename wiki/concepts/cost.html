工程效率與資源成本

定義

要比較架構，先固定需求、起始版本、環境與品質門檻，分開觀察經過時間、人工介入、運算資源與重試。

原理與工程用途

【公開技術文件】 P20 用可重複資料集及準則比較流程。U07 【個人直接觀點】 關心實際交付及目標效益。建議將等待、整合與失敗嘗試保留在紀錄中；多個 Worker 的工時相加無法代表牆鐘時間。

適用條件與限制

U10 【證據待補】 原時間公式與前提未取得。Dungeon Lab 只有功能測試；多 Agent 是否更快仍是 【待驗證假設】。需在相同門檻下重複對照，才能對相應任務範圍下結論。

延伸閱讀

工程品質與驗證、Task DAG 與動態調度、專案架構、角色與 Agent 數量。

來源：P20、P01、U-C（來源回執）。

本頁研討題：現有資料能否證明某種多 Agent 架構一定比單 Agent 更有效率？

何時將一次經驗提升為長期資產

【教學編排】 第一次成功先保留任務、環境及結果。再次遇到相同問題，找出穩定前提與反例，再選資產形式：專案約束進 AGENTS.md；可重複操作寫成 Skill；固定交付資訊做成模板；架構選擇與取捨寫決策紀錄；可判定的錯誤加入回歸測試。一次 Prompt 可能依賴當時上下文、版本或權限，無法直接推論可泛用。

例：第二次遇到同一交接遺漏，先試用含基準 commit 與測試結果的模板。於另一任務核對能否查回產物，再指定維護者、適用範圍及版本；工具改版後重驗，無效或衝突時修訂、降級或淘汰。模組規則留在模組，可以跨專案重現的做法才提升至共用層。

【公開技術文件】 P05 支持專案規範，P17 支持將可執行約束留在 repository。U09 【歷史研究整理】 反映保留私人管理資產的方向。【待驗證假設】 效益應在相近需求及品質門檻下比較重用率、首次成功率、人工介入、返工與維護時間；固定節省幅度尚無量化證據，U10 原式仍缺。

來源：S05（來源回執）、P05、P17、U-B（來源回執）。

【教學編排】 對照操作案例：品質達標後，怎樣比較工程成本？。
