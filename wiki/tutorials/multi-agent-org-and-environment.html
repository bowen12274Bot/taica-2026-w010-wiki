T05｜先畫責任與工作區，再決定開幾個 Agent

學習問題與先備

【教學編排】 能描述 B0 的 API 與畫面。若兩人同時改同一個尚未定案的欄位，即使有兩套工作目錄也可能一起返工。

技術與方法依據

【公開技術文件】 P14 的 worktree 共享 repo 物件及多數 refs，保有各自檢出與 index。P15 討論人類團隊，將其映射至 Agent 是 【工程設計】。U07 【個人直接觀點】 先定責任和環境，再按需求派工。

操作順序與資料流

【合成教學案例】 Human 核准目的與介面 → Coordinator 管依賴與所有者 → API/UI Worker 各交局部變更 → Reviewer 查契約 → Integrator 在目標基線驗證 → Human 接受。

  1. 【合成教學案例】 列出固定項：repo todos、起始 B0、權威分支 main。從 B0 為 API 與 UI 各開分支及 worktree；兩個 session 的 cwd 和基準各自記錄。共享服務、埠與測試資料仍需安排。

  2. 【合成教學案例】 先看介面是否穩定。未定時由一個責任人釐清；規格明確且 fixture 已凍結，API 與 UI 可並行。若兩票共改資料結構，先串行處理契約。

  3. 【合成教學案例】 評估可同時驗收的工作數、交接次數、合併與重跑代價。小變更可由一位 Agent 兼 Worker 與 Integrator；高風險改動另設 Reviewer。角色可長期沿用，session 可結束。

  4. 【合成教學案例】 以 DAG 標明哪些節點可開始；Integrating 之前核對兩份 commit 的共同祖先與契約版本。只有通過整合並獲准，才把新基線記為 B1。

適用範圍與反例

【證據待補】 無通用最佳人數，亦缺使用者完整自主組織 trace。

自我驗收

【教學編排】 UI 與 API 都在等同一個欄位定義，再多一個 Worker 有幫助嗎？

判斷依據：先解除共享依賴；只有可獨立完成且有驗收輸出的工作，才可能抵銷協調成本。
