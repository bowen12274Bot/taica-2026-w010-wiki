T04｜一次修完標籤篩選：從需求到交付

學習問題與先備

【教學編排】 會讀一份規格及一個測試結果。你要交付的是能操作的篩選功能，驗收資料得先於改碼準備好。

技術與方法依據

【歷史研究整理】 U02 的工作方式將 Chatbot 規劃和 Coding Agent 執行分開；【公開技術文件】 P05/P17 支持專案規範與自動回饋。U04 的 Planning Agent 契約屬 【工程設計】，無實作證明。

操作順序與資料流

【合成教學案例】 規格草案 → 人確認案例與排除項 → 基線 B0、Git 差異與測試入口 → 重現 → 最小修改 → 使用者路徑重測 → 交付。

  1. 【合成教學案例】 Chatbot 將「可依標籤看待辦」改寫成三個樣例：選 work 只見 A、清除後見 A/B、未知標籤顯示空結果。由產品負責人確認；不做批次改標籤。

  2. 【合成教學案例】 Coding Agent 查 AGENTS.md、當前分支和有無他人的改動，讀 API 及畫面處理器。先以 B0 fixture 建立失敗斷言，記錄命令與版本。

  3. 【合成教學案例】 在 Browser 點選，Network 若沒有 tag，先查前端組參數；若請求與回應正確但畫面仍舊，查 Console 與狀態更新。截圖留作版面證據；HTTP 200 尚未比對資料。

  4. 【合成教學案例】 只改確定的故障點，重跑 API 正負例、UI 清除操作與窄畫面。交付 diff、測試範圍、失敗或未測項。只有 terminal 時先驗證 API，把畫面標待驗。

自我驗收

【教學編排】 畫面只見 A，但固定資料本來就只有 A。怎樣讓證據有判別力？

判斷依據：加入非 work 的 B，先證明不帶條件會回兩筆，再測篩選及清除。把版本、命令與預期 ID 附到交付單。
