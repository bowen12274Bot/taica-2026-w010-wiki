T09｜品質達標後，怎樣比較工程成本？

學習問題與先備

【教學編排】 懂得整合後才能驗收。團隊想知道多開工作區有無收益，先寫出兩種方案都不能降低的品質門檻。

技術與方法依據

【公開技術文件】 P17 支持可執行架構約束；P20 支持以相同準則反覆評估，P28 支持 trace 定位。U07 【個人直接觀點】 關心人類審查負擔與目標；U10 【證據待補】 未提供時間公式。

操作順序與資料流

【合成教學案例】 目的：讓使用者找對待辦 → 契約：work 只見 A、清除見 A/B、未知標籤空清單 → 單元、API、UI 斷言 → 整合版本回歸 → 人類確認實際操作。

  1. 【合成教學案例】 分開記五級證據：Worker 自述、可定位 diff、指定測試結果、目標基線的整合結果、具權者接受。單元測試驗比對邏輯；API 測參數及資料；UI 測清除行為；架構檢查阻止越層。權限、破壞性變更與未覆蓋路徑留給人重點審查。

  2. 【合成教學案例】 另設執行記錄：開始與接受的時間點算牆鐘經過時間；人工介入分次計時；token 記工具報表；每次失敗重派、阻塞起訖、整合返工、交接遺漏各記一次及原因。平行 Worker 工時不可直接相加當牆鐘時間。

  3. 【合成教學案例】 固定需求、B0、工具／模型版本與品質門檻，單 Agent 和多 Agent 分別多次執行同組案例，記順序、失敗與未完成。先看品質是否都合格，再比較交付時間、人工與資源分布；無法控制的差異要揭露。

  4. 【合成教學案例】 若兩次交接都漏清除測試，先加入回歸案例；重複操作再整理成 Skill，固定約束寫規範。換一張票重驗、指定維護者、記版本及維護工時，過期即修訂或淘汰。

適用範圍與反例

【待驗證假設】 減少返工可能有益，仍須扣除設計及維護成本。Dungeon Lab 原測項没有單／多 Agent 對照；不可據以填寫收益。

自我驗收

【教學編排】 甲的 Worker 很快但整合退回兩次，乙較慢卻一次達標，怎樣報告？

判斷依據：分別呈現產品驗收、經過時間、人工、token、返工及限制；缺值記缺值。一次觀察不能證明普遍優劣。
