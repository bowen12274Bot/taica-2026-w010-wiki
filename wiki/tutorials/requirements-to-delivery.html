T06｜讓第二項需求接上同一個專案

學習問題與先備

【教學編排】 讀過角色及 B0 基線。要將一個需求交給數個執行者，你必須讓下游在不用猜介面的情況下開始工作。

技術與方法依據

【公開技術文件】 P13（Orca 文件查閱 2026-11-21，Experimental）區分 Run、Task、Dispatch。P16 manager 保有主控並呼叫專家；handoff 把控制權交給接手者。Sequential／Parallel 說明時序，與誰最終回覆分開選。

操作順序與資料流

【合成教學案例】 需求一 → F0 契約 → {F1 API ∥ F2 UI} → F3 整合 → 接受 B1 → 需求二 → 新契約與工作票。任何節點缺輸入可轉 BLOCKED；驗證失敗退回相應票。

  1. 【合成教學案例】 人類確認樣例與相容性；F0 寫下參數 tag、回傳 ID 與省略條件的行為。這份契約和 fixture 讓前後端可各自測，不必等對方完成才開始。

  2. 【合成教學案例】 依工作票標出 owner、base、依賴及輸出。人工可直接指定工作區；Coordinator 也可在授權內挑選 ready 票，記一次 dispatch，失敗再派時保留舊紀錄。

  3. 【合成教學案例】 F1、F2 各回傳差異、測試及限制；Reviewer 查介面，Integrator 將兩份產物放回同一目標基線，依 F3 實際操作。發現行為落差時退回責任票；通過後由授權者更新 B1。

  4. 【合成教學案例】 第二項需求「支援兩個標籤」重用 repo、角色、舊測試和 B1。AND／OR 尚未決定，先開新契約票；不沿用第一次派工的完成狀態。

適用範圍與反例

【工程設計】 U03 與 S02 支持協調方案；這個兩輪 Graph 是示例，缺少全程自治的實際觀察。

自我驗收

【教學編排】 Worker 已完成 F1，能否立即開始 F3？若接手者直接對人類回覆，又是哪一種控制方式？

判斷依據：F3 還需要 F2 和共同基準。接手者取得本輪主控屬 handoff；只向 Coordinator 交結果仍由 manager 綜合。
