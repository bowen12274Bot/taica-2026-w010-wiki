T01｜誰決定下一步？從模型輸出追到停止條件

學習問題與先備

【教學編排】 能讀懂一次輸入與輸出。面對「找出標籤篩選失敗原因」，先判斷是詢問文字，還是授權系統動手檢查。

技術與方法依據

【公開技術文件】 P01、P02：模型根據輸入產生文字或工具請求；runtime 檢查輸出類型並執行允許的動作，把觀察送回下一輪。Workflow 可由程式預定步驟；Agent 可依中途觀察選路。P17 的 harness 包含專案規則、工具與可執行的回饋。

操作順序與資料流

【合成教學案例】 問題 → harness 組裝 Context（指令、介面契約、可用工具）→ runtime 呼叫 Model → 工具請求 → 權限檢查 → Tools → 觀察回到 Context。模型也可直接輸出答案。

  1. 【合成教學案例】 讀 B0 的標籤規格。若只問「空清單應顯示什麼」，有契約即可直接解釋；若委託修復，先確認可改範圍，再開啟工具。

  2. 【合成教學案例】 固定路徑依序載入 fixture、呼叫 API、比對結果。動態路徑見到伺服器回傳正確，便改查 UI 的狀態更新；兩者都能用同一模型。

  3. 【合成教學案例】 模擬 trace：要求執行篩選測試 → 觀察找不到 fixture → 讀專案測試入口 → 改用正確路徑重試 → 發現應回一筆卻回兩筆 → 在授權範圍修正比對 → 重跑正例及未篩選回歸 → 留下待整合結果。

  4. 【合成教學案例】 若再次缺 fixture，記錄阻塞及缺少的輸入；若必須變更 API，停在批准點。runner 回傳最終輸出只表示本輪結束，交付另看驗收。

適用範圍與反例

【歷史研究整理】 U01 用 Prompt→Context→Harness→Loop→Graph 分析指令、可見資訊、執行環境、反覆修正及多任務依賴；此框架描述觀察角度。

自我驗收

【教學編排】 測試命令回傳零項測試，可否關票？

判斷依據：先核對測試是否被發現、基線與 fixture 是否正確；取得能區分預期及錯誤行為的斷言後才判定。
